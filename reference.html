Brief G

Submit a contact form

A visitor sends the contact form. Atlas checks it, saves the lead, then emails the team.

Inlets and outlets
  • Inlet Contact form · Send → Request runner Browser
  • HTTPS into Product Outlet Contact API
  • Operation Submit a contact form, stages in order:
  1. 1. Check the form is real runs public-guards
  2. 2. Save the lead runs lead-writer Database (SQL) → Neon · database (The database)
  3. 3. Email the team runs send-email HTTPS → Resend (A vendor’s endpoint)

Answer back: HTTPS Thanks message (never cached)

Today and the agreed target
  • The contact path checks the live form, consent and limits, saves the lead and contact records in one transaction, then sends mail.
  • Early refusals have no operation receipt yet; adding durable outcome receipts is agreed work.
FailureTeam seesTenant seesVisitor sees

Answer lost on the way backHTTPS · Unknown outcome: check before sending againThe lead may already be saved. Atlas checks before allowing a second send, so the same submission is never saved twice.One lead, not two.Sees “Checking…” then the thanks message, without retyping.
Form refused at the doorPermission check · Denied by Red Team: stops at onceThe outlet’s guards refuse it (form closed, consent missing or over the limit). Nothing is saved.Nothing new to do. Activity counts the refusals.Sees a clear message saying why it wasn’t sent.
Brief H

Offer and book an appointment

A visitor picks an office and a time. Atlas re-checks the slot inside the booking transaction.

Inlets and outlets
  • Inlet Booking form · Confirm → Request runner Browser
  • HTTPS into Product Outlet Schedule API
  • Operation Book an appointment, stages in order:
  1. 1. Re-check the offer runs schedule-offer
  2. 2. Lead + booking, one transaction runs booking-writer Database (SQL) → Neon · database (The database)
  3. 3. Tell other open forms runs availability-signal Live (WSS) → Live delivery (Live delivery service)
  4. 4. Send the confirmation runs send-email HTTPS → Resend (A vendor’s endpoint)

Answer back: HTTPS Confirmed, or “that time was just taken”

Today and the agreed target
  • The booking transaction already locks the office calendar and re-checks overlap.
  • Live availability signals to other open forms are agreed work (Section 3).

An editor publishes. Atlas commits the version, rebuilds only the affected pieces, then activates the ready page.

Inlets and outlets

  • Operation Publish and build, stages in order:

  2. 2. Build affected pieces runs node-renderer Store adapter → Output store (An output store)
  3. 3. Assemble and verify runs page-assembler
  4. 4. Activate the release runs release-activator Live (WSS) → Live delivery (Live delivery service)

Answer back: HTTPS Published, building, or failed (old version still live)

Today and the agreed target
  • Today Save replaces the draft and Publish freezes a page version; the node-HTML pipeline and durable refresh are agreed new work.
  • Recoverable draft history is an agreed addition (Section 2).

Brief D

Serve a website page

A visitor opens a page. Atlas returns ready HTML on a hit, or assembles it from cached and fresh pieces on a miss.

Inlets and outlets
  • Inlet Visitor opens a page → Request runner Browser
  • HTTPS into Product Outlet Public site
  • Operation Serve a page, stages in order:
  1. 1. Resolve the website runs site-resolver Database (SQL) → Neon · database (The database)
  2. 2. Look up the page runs page-cache Store adapter → Output store (An output store)
  3. 3. Render changed pieces runs node-renderer
  4. 4. Assemble the response runs page-assembler

Answer back: HTTPS Ready HTML + interaction shell

Today and the agreed target
  • Pages render today and are sent as no-store; a two-layer page and piece cache is agreed new work.
  • Private, personalised and live results always bypass shared HTML.
FailureTeam seesTenant seesVisitor sees
Cache missStore adapter · Cache miss: reuse what’s valid, render the restNot an error: unchanged pieces are reused and only missing ones are rendered.Nothing to do. The Cache view counts misses.Gets the page, a little slower.
Store unavailableStore adapter · Store unavailable: build fresh or keep the last good releaseThe store read fails. Atlas renders the page fresh and records the store failure.Cache view: “Storage had a problem; pages were built fresh.”Gets the page.

Type and shape

  • System type (SF Pro on Apple devices, Inter elsewhere). Sentence case everywhere; code names, versions and JSON stay monospace.
  • Large titles 32–44 px bold with tight tracking; body 15 px; captions 12–13 px in grey.
  • Cards 20–24 px radius on #F5F5F7; inset wells 14 px; capsules for buttons, chips and segmented controls; frosted glass for floating toolbars and sheets.
  • Green iOS switches; Atlas Blue for buttons and links; red only for Atlas Red Team; amber for “needs attention”.
  • Sheets follow iOS Settings: 44 px rows, inset hairlines, grouped lists.

Wire protocols

ProtocolWhen it worksWhen it fails
HTTPSRequest and answer over the networkA request goes out and one answer comes back.No answer in time: retry, then fall back to the next rung where the policy allows. An answer lost after the work was done is an unknown outcome, not a failure: check before sending again.
In-processA call inside AtlasOne part calls the next inside Atlas; the result comes back on the same wire.The called module crashes. The stage ends with a partial result; nothing is sent twice.
Record referenceA stored link, not a callA stage reads the exact version, deployment or host it points at.The record it points at is missing. The stage can’t start and is blocked.
Permission checkAtlas Red Team decidesThe red lock asks Red Team and enforces allow or deny before the work runs.Denied: it stops at once. No other rung or variant is tried.
Database (SQL)A transaction in the databaseReads and writes run inside one transaction that commits as a whole.A conflict (a slot already taken) rolls the whole transaction back. A database error is not retried at another endpoint.
Store adapterCache and output storageA read names its key, scope and freshness and comes back as hit, miss or bypass.The store is down: Atlas renders fresh output (or keeps the last good release) and records the store failure.
Stream (SSE)One-way stream over HTTPThe answer streams back piece by piece while it is written.The stream stops partway. What arrived is kept and the turn says it was cut short. The provider is not switched once streaming has begun.

Rules

Decisions from the briefs and from design review that every screen follows.

Honest outcomes (Section 3)

  • A retry that recovered stays invisible to the tenant.
  • A failed save shows unsaved work; never show Saved before it is durable.
  • A failed booking never appears confirmed.
  • A failed publication keeps the prior live release and says so.
  • An answer lost on the way back is an unknown outcome: check before allowing a resend.

Cache (Section 2)

  • One Cache tile per website: a quick switch and Publish; View holds costs, usage, active and pending settings, overrides and build status.
  • Pages and features inherit the website default unless overridden.
  • Form submissions, booking times, chat and calls always stay live; private or personalised output never shares HTML.
  • Publish, prepare, then activate. An older build never replaces a newer release; retry targets the same revision.
  • No invented provider bills: cost shows measured usage and labelled estimates.

Red Team

  • Red locks enforce at protected points; a UI lock only previews.
  • A denial stops at once; no other rung or variant is tried.
  • Identity and input validation are separate from authorization.

Content and data

  • Northline Home Services is fictional and always marked SAMPLE.
  • No vault entry names, keys, repo paths, commit hashes, database function names or real IDs on shareable pages.
  • Vendors appear as colour monograms, not their logos.
  • Plain words: name things by what people recognise.

Open items

Marked in the apps as amber “Still to specify”, or deferred by the briefs.

  • Stage ordering and data bindings; allowed fallback outcomes; write-result recovery; coherent run plans.
  • How a skipped stage reports; whether a blocked stage stops the whole run.
  • Activation, rollback and retention, including what runs after a recall or a failed activation; decision freshness and revocation; which effects run during a test.
  • Section 2: the first storage provider and its measured cost, budgets and retention; page templates and scheduled publishing are deferred.
  • Section 3: the notification centre UI, native apps and PDF import are outside this closure; exact budgets and host selection are engineering work.
  • Sections 4–6: portable rendering, classic blocks, permissions and rollout.
